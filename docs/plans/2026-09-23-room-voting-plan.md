**Room voting — implementation plan and status**

Status: implemented in the working tree, 23 September 2026. Verification coverage and remaining limits are recorded in [room voting verification](../verification/room-voting.md). Based on the current working tree and the [room-turn brief](../group-chat-turns-brief-2026-09-23.md).

**Proposed behavior**

A new room message starts an election with two separate inference phases: **proposals first, votes second**. Every active member first reads the same conversation snapshot and proposes who should reply and why, or why the task is complete. The server waits for all proposals, then supplies the complete set to every voter before any ballot is cast. After parallel voting (and a judge decision if tied) selects a speaker, that bot takes its normal working turn. Once its contribution settles, a fresh proposal-and-vote cycle starts from the updated conversation. Electing `task_complete` ends the discussion without another bot reply.

“Start from scratch” means fresh proposals, ballots and inference sessions. It does not erase messages, forget the original request, reset run budgets, or lose pending assignments. Historical election receipts remain inspectable.

Confirmed choices: voting replaces both ordinary room Chat and Goal / Finish together, elections repeat after every elected reply, and both proposals and votes run in parallel, with a separate judge model selected per room to resolve ties. All bots read the conversation and provide their explanation **before voting starts**, so every voter can consider everyone's reasons. Bot-to-bot DM channels and direct chats remain separate. The implementation follows these choices; provider inference was revised to use MCP submission tools following the user’s clarification.

**Proposal phase, voting phase, and tie handling**

1. Freeze active membership, conversation revision, candidate IDs and relevant settings. Archived/deleted members do not participate. Use stable bot IDs rather than names.
2. Each bot reads the conversation and independently submits a proposed speaker, including itself, plus a required reason, or proposes `task_complete` with a reason. Proposals run in parallel. Do not feed partially collected proposals to other proposers; they all start from the same evidence.
3. Wait for a valid proposal from every participant. Freeze and distribute the complete proposal set, in stable roster order, including every reason. **No vote starts before this barrier.** A proposal is not a vote and adds nothing to the tally.
4. Collect votes in parallel. Every voter sees the same conversation and complete proposals, but no partial votes. Ballots contain only a candidate; do not repeat a reason.
5. Tally one vote per active member. A unique plurality wins. On a tie, call the room's selected judge model with context, proposals, all votes, and only the tied leading candidates. Require its winner and a short public reason. A failed/invalid judge pauses the discussion, without a fallback winner. Automatic judge selection uses the first active member's model; group details can pin another compatible provider/model.
6. Give the elected speaker the conversation, all proposals/reasons, votes and judge decision. After its contribution, repeat from updated history. Keep the audit trail in the transcript and in later model context. Superseded and interrupted rounds remain labeled as such.

Example: A votes B, B votes C, C votes A. All three have one vote; the judge reads their proposals and history and chooses A, B or C with a reason. If B wins, only B takes a working turn, then a new parallel election starts.

This produces a unique winner after a valid judge decision, not necessarily a majority. The judge has discretion among tied leaders only. Proposals never count as votes. Cancellation or provider failure aborts and drains sibling calls before retrying or pausing.

**Required reasons before voting**

Each proposal contains a proposed candidate ID (or `task_complete`) and `reason`, a trimmed nonempty string of at most 500 characters, normally one or two sentences. A self-proposal explains what the bot can contribute next; a teammate proposal explains what that teammate should add and why the conversation calls for it. A completion proposal explains what is already answered or delivered and why another reply adds nothing. The later ballot contains only a candidate. A tie-breaking judge must supply a reason. The server enforces schema and bounds; whether a reason is useful requires model-quality evaluation.

Example after a discussion about a failed login test, **before any votes**:

- A proposes B: “The login test is still failing, and B implemented this flow. B should inspect the failure and explain the fix.”
- B proposes C: “C reproduced the failure and has the latest logs. C should identify which assertion fails before I change the implementation.”
- C proposes itself: “I have the reproduction details and can clarify the failing assertion, which has not been explained in the conversation.”

All three bots receive all three proposals. Only then do all three vote in parallel. A can vote C after considering the others' explanations, despite originally proposing B. There are no votes to tally during proposals.

Every voter has the same candidates. Only the judge is restricted to tied leaders; its reason is retained with the result.

The expandable election card has **Proposals**, **Votes**, and conditional **Judge** sections: proposal reasons, candidate-only ballots, and the judge decision/reason. Persist both records with election ID, phase, round, author, candidate, order and conversation revision. Neither phase produces ordinary conversational messages or triggers another election. All voters see the frozen current proposals, including their own, and no partial current ballots. Historical proposals, votes and judge reasons are included in later conversation context, subject to the shared context budget and summarization. Missing/blank/oversized reasons use the bounded repair/pause policy; never supply a fabricated reason or begin voting with missing proposals. Completed or cancelled elections retain their audit records.

**Context, execution, and cost**

Every voter reads the conversation itself, not just the newest message or a tally. Provide the full current room-task conversation when it fits, together with the original request, room bulletin, member roles, and retained result reports. For longer histories, build one shared bounded packet containing an explicitly labeled summary of older discussion plus recent messages verbatim, preserving decisions, unanswered questions, corrections and completed work. Keep the original request pinned even after it leaves today's 30-entry window. Fit that common packet to the smallest participating context capacity and reserve space for every current proposal and reason plus the ballots and judge decision. Cache it by conversation revision so voters do not get independently generated summaries. Context overflow or summary failure must not silently reduce a ballot to the latest message; pause if a valid shared packet cannot be built. Summary generation is additional model work and must be accounted for separately from the ballot-count estimate below.

Preserve attachments through supported image input or shared textual references; a voter that cannot inspect an attachment must not claim it did. Personal identity and standing instructions may differ, but shared conversation evidence must have one revision. Do not load unrelated private conversations solely to vote. Public reasons must be grounded in the supplied room evidence and roster, without disclosing private memory. Any new message invalidates the snapshot according to the restart rules below.

Proposals and votes use private, fresh provider turns on each bot’s selected model and account. Each turn mounts a phase-specific MCP submission tool through the existing agents integration (`submit_proposal` or `cast_vote`); a private loopback endpoint enforces identity, phase, allowed candidates, required reasons, single submission and expiry. No normal app working integrations are mounted. The turn uses Ask permissions, an empty temporary working directory, and denies non-election permission requests. Provider-native tools are not universally removable; this is not a claim of a tool-free runtime or an OS sandbox. Room authority is enforced by the server: private turn prose cannot become a vote or chat reply. Do not substitute a title-generation model. Store only structured submissions and brief public reasons in the room receipt.

The optional `ProviderInstance.generateText` is not used: it has no selected-model argument or usage result and is not uniformly available. The shared inference helper instead calls the normal provider adapter with the bot’s model/effort/variant selection, a private thread, cancellation, and phase-scoped MCP tools. Drivers with pooled sessions expose a general session-release hook so temporary voting sessions do not accumulate. An engine lacking the existing agents MCP integration pauses explicitly; no fabricated ballot or substituted model is allowed.

Voting needs explicit reservations that respect bot/provider capacity without overwriting an unrelated turn's busy state. A busy voter waits within a bounded preparation window; no election may hold reservations on all bots while waiting on one. Release reservations after each proposal or ballot call; never hold a proposal reservation while waiting for the phase barrier. The elected speaker is rechecked and claimed atomically before its normal working turn.

For N bots and R replies followed by a completion election, two inference phases require **2 × N × (R + 1) + R** logical provider turns. MCP tool exchanges may involve additional underlying model requests. Three bots producing one reply require 13 logical provider turns; ten bots producing five replies require 125. Each election uses N proposal calls and N vote calls, even if it elects completion. Each tied round adds one judge turn. Retries, summaries and delegated work add more. Track both phases in usage/spend accounting, keep outputs short, bound history, and display proposal and voting progress. Parallel proposals and parallel votes reduce latency but not call count; candidate-only ballots reduce output.

Current starting limits (constants in `server/room-election.ts`): 30 seconds per proposal or ballot, one repair attempt for malformed output, 60 seconds to wait for an occupied bot, 10 elected contributions per run, and a 20-minute active orchestration budget. Existing speaker deadlines still apply; time awaiting a human approval is separate. These limits can be tuned without changing the voting protocol. Exhaustion pauses the run with a reason and explicit Resume, which starts a new bounded run.

**Events and integration boundaries**

- Human messages and accepted `post_to_room` messages trigger elections in voting rooms. Preserve the original sender and unattended provenance; a bot post never becomes human authorization.
- An elected contribution triggers the next election only after its complete provider turn and accepted downstream work settle. Streaming chunks, tool activities, proposal/voting receipts, reactions, title changes, and goal-control messages never trigger elections.
- A new external message arriving during proposing, voting or judging invalidates both phases and restarts with fresh proposals from the updated conversation. Never mix reasons from one revision with votes from another. Coalesce bursts and bound invalidations so a busy feed cannot burn unlimited ballots. New human messages take priority. During speaking, queue them; include them before the next election. Steering must invalidate any pending election and retain its existing engine support checks.
- Give every event and run stable identities. HTTP retries, reconnects, and duplicate provider events cannot produce extra elections or replies. Carry one originating-run identity across automated posts and rooms so posting cannot reset reply/time budgets. Keep existing posting eligibility, approval and anti-loop checks.
- In shared rooms, mentions express whom the message concerns; they no longer directly grant a speaking turn. Replace ordinary default-responder routing and chained-mention dispatch. Remove the Chat/Goal picker and obsolete responder controls; explain the election behavior in the composer.
- Only one scheduler may own a room at a time. Replace the Goal coordinator loop with voting, and integrate existing room queues and handoffs with that ownership.
- Accept legacy `channelMode: chat | goal` requests from older clients, saved drafts and queued messages, but route both into voting. Retain historical messages and Goal receipts. Retire old responder/coordinator fields without destroying historical data or silently reinterpreting them as voting privileges.
- Scheduled team goals also enter voting. Preserve their pinned background task, routine run ID, unattended restrictions, stop behavior, completion notifications and durable outcome receipts. The previously configured coordinator can remain the routine's owner/contact, but does not automatically get the first vote or speaking turn. Adapt `goalState`, `startGoal` and `finishGoalRun` so an individual ballot or reply never prematurely completes a scheduled run. Map completion, needs-human-input, blocked/paused, limits, cancellation and restart interruption explicitly.

Delegation needs an explicit compatibility boundary. Proposed first-version policy: same-room `coordinate_bots` is unavailable, including routing members into their direct threads or indirectly through outside specialists, because it would move the discussion outside elected public turns. A bot can request another member's contribution in its reply, which the next election considers. Only work for specialists outside the originating room can target direct bot conversations; the election parks while results return and the originally elected bot finishes its contribution. Incoming addressed handoffs into shared rooms should be refused clearly rather than silently changing their named recipient; the caller can explicitly choose direct delivery. This changes existing room-delegation behavior and must be visible in tool definitions and migration notes. Supporting guaranteed named assignments inside an elected discussion requires a separate distinction between work ownership and speaking rights; it must not be added as an unnoticed scheduler bypass.

**Failures and lifecycle rules**

| Situation | Proposed behavior |
| --- | --- |
| No active members | Idle/unavailable receipt; no inference. |
| One active member | It chooses itself or Task complete; all run limits still apply. |
| Invalid proposal/ballot, missing reason, forbidden ID, timeout, offline provider | One bounded repair where appropriate; otherwise pause with the failed voter named. No invented vote, random winner, or automatic completion. |
| Bot busy beyond its wait cap | Pause; leave its other conversation untouched. Everyone must provide a valid proposal and actually vote for a completed election. |
| Winner becomes busy/unavailable after voting | Bounded wait or invalidate/re-elect after a genuine eligibility change; no silent runner-up substitution. |
| Membership/model/permissions change | Invalidate before dispatch and rebuild from fresh records; bound repeated restarts. |
| Human approval/question opens during speaking | Pause elections while the person decides. Do not treat silence as completion. |
| Failed/interrupted speaker or empty successful reply | Record the actual outcome and pause rather than automatically creating an endless retry election. |
| Repeated replies, self-selection, or A/B oscillation | Permit legitimate repeat speakers, but stop at budgets; detect repeated normalized content as an additional pause condition, not proof of failure. |
| Stop, deletion, or access revocation | Cancel proposal and ballot calls, pending elections, and the owned speaker/handoffs as appropriate; fence late results by run and generation IDs. |
| App disconnect | Server remains owner; clients recover the same persisted run state. |
| Server restart | Mark in-flight runs interrupted; do not replay votes or tool-bearing work automatically. |
| Room task switches/history edits | Pin execution to its original thread and branch; incompatible edits invalidate or stop that run. Never append into the newly selected task accidentally. |

**Implementation sequence**

1. Define the voting protocol, legal-final-ballot calculation, state machine, and persistence records in dedicated modules. States include proposing, voting, judging, waiting, speaking, waiting for delegated work, completed, paused, cancelled, and interrupted. Voting becomes the shared-room execution model; keep bot-to-bot DM channels separate. Preserve historical data and compatibility with legacy Chat/Goal requests. Do not convert an actively executing old run midway through a contribution.
2. Implement cancellable proposal and ballot turns using the existing MCP integration, with correct selected models, capacity admission, usage, and spend limits. This is the largest provider compatibility dependency.
3. Integrate election ownership with `startGroupTurn`, the existing room queue and `runGroupMemberTurn`. Reuse speaker resources, permissions, attribution, deadlines, and cancellation; replace only the responder-selection loop in voting rooms.
4. Connect human sends, bot posts, scheduled routines, queue draining, branch revisions, handoff boundaries, and restart recovery to the same run state. Add generation checks before every state transition and speaker claim.
5. Update desktop and companion/mobile contracts and rendering: “Gathering proposals 2/3,” “Voting 2/3,” “B selected,” expandable proposal reasons, candidate-only ballots, and tie-breaking judge decisions, speaking/waiting/paused/completed state, and Stop/Resume. Remove the Chat/Goal split and responder controls. Older clients must get a readable activity fallback. Do not show raw ballot JSON as chat replies.
6. Verify against disposable fixtures, then replace existing room behavior in the release. Document compatibility and migration behavior. No mutations against the user's live app or data during verification.

**Verification required before calling it complete**

Use the [verification workflow](../verification/README.md). Exercise deterministic fake-model ballots through the real API and clients in an isolated fixture. Cover the three-bot example; arbitrary electorate sizes and tied and unique plurality tally shapes; initial and later completion; invalid ballots; busy/removed bots; provider integration isolation and selected model; usage accounting; queued/steered messages; posts and cross-room loop bounds; delegation boundaries; duplicate delivery; cancellation at every phase; late events; restart; task switching; and desktop/mobile state recovery. Verify private voting events never leak into the conversational transcript and no app working integrations are mounted.

Retain API evidence, transcripts, state transitions, and logs. Update room-routing, Goal and posting expectations deliberately for the new behavior; preserve checks for resources, permissions, cancellation, attribution, scheduled runs, direct-chat coordination and bot-to-bot channels. Add migration tests for existing rooms, scheduled team goals, historical receipts, queued sends and older clients. Scripted fixture success proves orchestration; real-model voting quality and completion judgment require a separately scoped evaluation.

Reason/context acceptance checks must prove that each proposer receives the same conversation revision, and no voting call begins before every valid proposal is present. Inspect the very first voting prompt to prove it includes all candidates' proposals and reasons. Test concurrent proposals completing out of order, a missing/slow proposal, new input between or during phases, a voter changing its proposed choice, stale/duplicate proposal results after cancellation, and the winner receiving the complete election brief. Also test missing/blank/oversized reasons; self, peer and completion proposals; judge candidate restrictions and required reasons; long-history summary reuse and original-request retention; persistence/reconnect for both phases; and inclusion of election records in conversation context without triggering elections. The next round must include the completed reply and regenerate all proposals. Evaluate reason relevance separately using scenarios where earlier conversation or another bot's proposal changes who should reply.
